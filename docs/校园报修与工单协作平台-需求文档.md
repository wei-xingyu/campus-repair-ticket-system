# 校园报修与工单协作平台需求文档

## 1. 项目概述

### 1.1 项目背景

校园中的宿舍、教室和公共区域会持续出现照明、门锁、桌椅、供水等设施故障。传统的电话、微信群或口头报修容易漏单，报修人也难以了解处理进度；维修人员缺少统一的待办列表，管理员难以追踪派单和处理时效。

本项目为校园提供一个前后端分离的报修与工单协作平台。报修人提交问题，管理员分派给维修人员，维修人员记录处理过程并完成工单，报修人确认结果并评价。系统保留完整状态历史，便于追踪责任和统计处理情况。

### 1.2 项目目标

- 让报修人能提交、查看和跟进本人报修。
- 让管理员能按位置、类型和优先级分派工单。
- 让维修人员能管理自己的工单并记录处理结果。
- 让每次状态变更都可追溯，避免无记录地修改工单。
- 通过服务端权限、参数校验、事务和自动化测试保证基本可靠性。

### 1.3 项目范围

MVP 面向单个学校或单个校区，使用统一 Web 管理端。首期不做移动端小程序、支付、实时聊天、多校区租户、短信平台、复杂排班、微服务和高并发架构。

## 2. 用户角色与权限

| 角色 | 说明 | 主要权限 |
|---|---|---|
| 报修人（STUDENT） | 提交报修并跟踪本人请求 | 创建工单；查看本人列表和详情；在允许的状态下取消；确认完成并评价 |
| 维修人员（REPAIRER） | 接收管理员分派的维修任务 | 查看分派给自己的工单；接单、拒绝、开始处理、提交处理结果 |
| 管理员（ADMIN） | 管理工单分派和基础数据 | 查看全部工单；派单、转派、关闭；管理用户、楼宇和设备；查看统计 |

权限必须在后端校验。前端隐藏按钮只用于改善界面，不构成安全控制。用户不能通过修改 URL 或请求体读取其他用户的工单。

## 3. 核心业务规则

### 3.1 工单状态

| 状态码 | 状态名称 | 含义 |
|---|---|---|
| PENDING_ASSIGNMENT | 待派单 | 报修已提交，等待管理员分派 |
| PENDING_ACCEPTANCE | 待接单 | 已分派，维修人员尚未接单 |
| ACCEPTED | 已接单 | 维修人员已接受任务 |
| PROCESSING | 处理中 | 维修人员已开始处理 |
| PENDING_CONFIRMATION | 待确认 | 维修人员已提交处理结果 |
| COMPLETED | 已完成 | 报修人确认处理完成 |
| CANCELLED | 已取消 | 报修人在处理开始前取消，或管理员取消 |
| CLOSED | 已关闭 | 管理员关闭工单，不再继续处理 |

允许的主要状态变化：

```text
待派单 -> 待接单 -> 已接单 -> 处理中 -> 待确认 -> 已完成
                  |                       |
                  -> 待派单（拒绝动作记入历史） -> 处理中（报修人要求重新处理）

待派单 / 待接单 / 已接单 -> 已取消
除已完成、已取消、已关闭外，管理员可关闭工单
```

任何不在上述规则中的状态变化都应拒绝，并返回明确业务错误。状态变化、工单当前状态、处理人更新和状态历史记录应在同一数据库事务中完成。

### 3.2 业务约束

1. 工单编号由服务端生成，客户端不得指定。
2. 报修人只能操作或查看自己创建的工单；管理员可以查看和管理全部工单；维修人员只能查看分配给自己的工单。
3. 首期允许附件图片最多 5 张，单张不超过 5 MB；服务端需检查文件类型和大小。文件可先保存到本地上传目录，数据库只存储访问路径。
4. 维修人员拒绝任务必须填写原因。完成处理必须填写处理说明；可选上传处理前后图片。
5. 报修人只能在工单处于“待派单、待接单、已接单”时取消；进入处理中后不能直接取消。
6. 报修人只能对“待确认”工单确认完成或要求重新处理。要求重新处理需要填写原因，并将工单转回处理中。
7. 每一次成功的状态变化都写入工单历史；失败操作不得留下半条历史记录。
8. 派单、接单、拒绝、开始处理、完成提交等写操作需要考虑重复请求。通过当前状态条件更新或版本号防止并发操作覆盖彼此。
9. 删除用户或设备不得级联物理删除已有工单和历史记录；MVP 可采用停用状态。
10. 统计时间按学校本地时区处理，接口时间统一使用 ISO 8601 日期时间字符串。
11. MVP 默认 SLA 为工单创建后 48 小时，可通过配置调整；超时定义为超过 `sla_due_at` 且工单仍未完成、取消或关闭。创建时保存截止时间，避免后续修改配置改变历史工单口径。
12. 每张已完成工单允许报修人提交一次 1–5 分评价，可附 500 字以内说明。

## 4. 主要业务流程

### 4.1 报修流程

1. 报修人登录系统。
2. 选择楼宇、房间和故障类型，填写标题、问题描述及优先级，可添加图片。
3. 系统校验数据后创建工单，初始状态为“待派单”。
4. 管理员查看待派单列表并选择维修人员。
5. 维修人员接受或拒绝；拒绝时填写原因，工单回到待派单。
6. 接受后维修人员开始处理，记录处理说明和结果。
7. 报修人确认完成，或要求重新处理。
8. 系统保留完整状态历史和操作人信息。

### 4.2 转派流程

管理员可将“待接单”或“已接单”工单转派给其他维修人员。转派后状态回到“待接单”，当前处理人变为新维修人员，写入一次状态/分派历史；旧维修人员不再有该工单操作权。

## 5. 功能需求

### 5.1 登录与个人信息

- 通过账号和密码登录；系统根据账号角色加载对应页面权限。
- 支持退出登录和查看当前用户信息。
- 密码必须加密保存；登录失败不泄露账号是否存在等敏感信息。
- 登录成功后签发随机 Token，Redis 保存用户身份和角色。前端将 Token 保存在当前标签页的 `sessionStorage`，后续通过 `Authorization` 请求头携带。有效登录态访问时续期至 30 分钟，退出删除当前 Token 对应的登录态。
- 本地初始化报修人、维修人员、管理员三种测试账号，并分别保留三个独立会话，方便切换角色验证权限；生产账号和密码不得写进仓库。

### 5.2 工单管理

- 报修人创建工单，分页查看本人工单，查看工单详情和历史。
- 管理员按状态、故障类型、楼宇、优先级、创建时间、报修人等条件查询全部工单。
- 管理员派单、转派和关闭工单。
- 维修人员查看分派给自己的工单，执行接单、拒绝、开始处理和提交处理结果。
- 报修人确认完成或要求重新处理。
- 报修人可对已完成工单提交一次评价。
- 管理员可查看工单完整操作历史。

### 5.3 基础数据管理

- 管理员维护楼宇和楼栋房间信息，支持启用/停用。
- 管理员维护故障类别（如水电、门窗、网络、家具、其他），支持启用/停用。
- 管理员维护维修人员账号和角色状态。
- 停用的基础数据不可用于新建工单，但历史工单仍保留原有名称快照或关联信息。

### 5.4 统计看板

管理员查看按时间范围统计的工单总量、待派单量、处理中量、已完成量、已超时量、平均处理时长和各故障类型数量。超时口径采用工单创建时记录的 `sla_due_at`；当前统计直接由 MySQL 聚合查询提供。

### 5.5 Redis 查询缓存（已实现）

| 接口 | Redis key | 逻辑有效期 / Redis TTL | 写入后失效 |
|---|---|---|---|
| `GET /tickets/{id}` | `cache:ticket:detailed:{id}` | 10～20 分钟 / 20～30 分钟 | 创建及 10 个状态变更操作在 MySQL 事务提交后删除对应详情。 |
| `GET /categories` | `cache:categories:enabled` | 30 分钟 / 40 分钟 | 新增、修改或启停分类写库后删除启用分类列表。 |
| `GET /buildings` | `cache:building:enabled` | 30 分钟 / 40 分钟 | 新增、修改或启停楼宇写库后删除启用楼宇列表。 |
| `GET /buildings/{buildingId}/assets` | `cache:building:asset:{buildingId}` | 10 分钟 / 20 分钟 | 设备新增、修改或启停后清理所属楼宇。跨楼宇迁移清理原楼宇和目标楼宇。楼宇启用状态变化也清理该楼设备列表。 |

四类缓存均按需回填。工单工作台加载时请求分类和楼宇列表，报修表单选择楼宇时请求该楼设备列表。首次查询未命中时回源 MySQL。逻辑过期时可先返回旧值，并由取得锁的后台任务重建。Redis 实际 TTL 比逻辑有效期长 10 分钟，供旧值读取和后台重建使用。工单详情每次回填的逻辑有效期在 15 分钟基础上随机加减 0～5 分钟。

工单详情包含基本信息、报修附件和操作历史。命中缓存后仍根据数据库当前归属校验权限，无权限返回 HTTP `403`。不存在的工单短时缓存空值 1 分钟，并返回 HTTP `404`。列表查询的空数组 `[]` 是有效结果，按列表的正常时长缓存。设备列表查询保留楼宇存在性检查，楼宇已停用时设备查询结果为空。

管理员维护列表、工单分页和统计看板当前直接查 MySQL。统计的超时数依赖当前时间，即使没有写操作也可能变化，刷新时执行实时查询。并发场景下，已读到旧值的后台任务仍可能在删缓存后回填旧数据。

## 6. 非功能需求

- 所有业务写接口进行服务端参数校验并返回统一错误结构。
- 所有用户身份和数据范围由后端确认；不信任请求体中的用户 ID 或角色。
- 数据库使用 InnoDB；工单状态与历史记录保持事务一致。
- 关键写操作记录操作人、时间、对象和结果；日志不得记录密码、token 或完整敏感内容。
- 列表接口必须分页；查询条件使用参数绑定，不拼接用户输入 SQL。
- 对工单编号、用户名等业务唯一字段设置数据库唯一约束；根据常用筛选条件设计索引。
- 代码提供核心业务单元测试和接口集成测试，重点覆盖权限、非法状态变化、事务回滚和重复/并发操作。
- 提供本地运行说明、环境变量示例、数据库初始化脚本和部署说明。

## 7. 当前进度与 MVP 验收标准

截至 2026-11-10，账号登录、工单创建与流转、基础数据维护、图片上传和统计查询已具备实现。Redis Token 登录已完成前后端联调。工单详情、启用分类、启用楼宇及楼宇设备列表已接入缓存，其中设备缓存联调已通过。以下验收项用于回归检查各角色权限与缓存失效。

1. 三种角色能够登录，并且未登录请求无法访问受保护接口。
2. 报修人可以创建工单并且只能查询本人数据。
3. 管理员能够查询全部工单并进行派单、转派和关闭。
4. 维修人员只能操作分派给自己的工单，能够完成接单、拒绝、处理和提交结果。
5. 报修人能够确认完成或要求重新处理。
6. 非法状态变化返回明确错误；并发重复操作不会产生重复历史或错误状态覆盖。
7. 每次成功状态变化都有对应历史记录；事务失败时工单和历史均回滚。
8. 前端能够走通报修人、管理员、维修人员的主要操作流程。
9. 提供数据库初始化、配置说明、测试结果和可重复部署步骤。

10. Redis 登录验收覆盖请求续期和退出后旧 Token 返回 `401`。详情缓存验收覆盖首次回填、命中权限校验、写操作提交后失效，以及不存在的 ID 重复查询仍返回 `404`。
11. 分类和楼宇列表重复查询应命中 Redis，启停后下一次查询应反映新状态。验证设备跨楼宇迁移后两侧列表正确，以及停用楼宇后设备列表为空。

## 8. 建议开发阶段

1. 项目与测试数据：创建数据库和初始化脚本，准备三类角色测试账号及楼宇/类别数据，确认应用可启动。
2. 通用后端基础：统一响应、参数校验、异常处理和日志脱敏。
3. 登录会话：完成登录、当前用户和退出；保存三种角色的 Token，后续接口测试通过请求头复用。
4. 权限底座：认证拦截、角色校验和数据范围校验。
5. 基础数据接口：先完成类别、楼宇和维修人员查询，再提供管理员维护接口。
6. 工单基础接口：创建、分页列表、详情和状态历史查询。
7. 工单流转接口：按状态顺序实现派单、接单/拒绝、开始处理、提交结果、确认/重开、取消/关闭。
8. 附件和统计：完成图片上传与 MySQL 统计查询。
9. 前后端联调：前端登录后通过 Token 保持会话，按三个角色走通业务流程。
10. 质量与部署：补测试、运行说明、Docker Compose 本地依赖、Linux 服务运行和 Nginx 代理。
11. 有业务依据的扩展：根据第 10 节推进登录态撤销、回归和性能验证，按需评估超时提醒。

## 9. 明确暂不做的内容

MVP 暂不做微服务、分布式事务、消息队列、全文搜索、实时协同编辑、复杂排班、支付、短信/邮件第三方服务和小程序。只有在核心流程完成并有明确业务需求后再评估。

## 10. 后续开发建议

| 优先级 | 开发项 | 完成标准 |
|---|---|---|
| P1 | 停用维修员后撤销已有登录态 | `PUT /admin/repairers/{id}/status` 停用成功后，同一账号的多个旧 Token 请求受保护接口均返回 `401`。重新启用后，旧 Token 仍不可用，新登录可以获得新 Token。当前只在登录时检查账号启用状态。 |
| P1 | 补齐楼宇回归测试和参数保护 | 给新增楼宇测试注入 Redis mock，断言删除的 key。将修改楼宇的空请求与缺少名称分开处理，空请求返回参数错误，单独缺少名称保留原名称。 |
| P2 | 验证缓存并发失效 | 复现后台重建与写操作同时发生的场景，验证旧数据是否会在删除后写回。根据复现结果决定是否加回填保护，并验证事务回滚、设备跨楼宇迁移和楼宇停用。 |
| P2 | 补充缓存运行指标与回归 | 记录命中、回源、重建失败和 Redis 超时，便于定位异常。补齐命中权限校验、空值 `404`、更新失效等测试。 |
| P2 | 统计与工单分页性能排查 | 统计保留实时 MySQL 查询。用代表性数据和筛选范围检查聚合 SQL、分页 SQL 的耗时、执行计划和索引。 |
| 按需 | 管理列表、楼宇和设备单条详情缓存 | 当前保留 MySQL 查询。实际出现频繁重复查询或明显慢查询时再评估，并为筛选条件、权限和写后失效制定规则。工单分页暂缓加入 Redis。 |
