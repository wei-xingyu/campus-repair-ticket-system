   信息 # 校园报修与工单协作平台接口文档

> 本文档参考教培后台项目的接口文档组织方式，按业务模块描述请求路径、请求方式、参数、统一响应和示例。本文是 MVP 的接口约定；字段和权限以本文为准，后续实现时若需调整，应同步更新文档。

## 1. 通用约定

### 1.1 基本信息

- 本地 API 前缀：`/api`（由前端开发代理或 Nginx 转发）；后端 Controller 路径不包含 `/api`。
- 数据格式：请求和响应均使用 `application/json`；文件上传使用 `multipart/form-data`。
- 字符编码：UTF-8。
- 日期时间：ISO 8601，例如 `2026-10-19T14:30:00`；服务端和数据库按学校本地时区解释。
- 分页页码从 `1` 开始，`pageSize` 默认 `10`，最大 `100`。

### 1.2 统一响应结构

成功响应沿用现有后端项目的 `code/msg/data` 结构：`code=1` 表示业务成功，`code=0` 表示业务失败。

```json
{
  "code": 1,
  "msg": "success",
  "data": {}
}
```

业务失败示例：

```json
{
  "code": 0,
  "msg": "工单当前状态不允许此操作",
  "data": null
}
```

建议同时使用正确 HTTP 状态码：未认证 `401`，无权限 `403`，资源不存在 `404`，参数校验失败 `400`，业务状态冲突 `409`，服务端异常 `500`。若项目实现阶段选择所有业务响应均返回 HTTP 200，必须保证前端还能可靠地区分网络/HTTP 错误和 `code=0` 的业务错误；推荐采用上述 HTTP 状态码语义。

### 1.3 分页响应

```json
{
  "code": 1,
  "msg": "success",
  "data": {
    "total": 36,
    "rows": [],
    "page": 1,
    "pageSize": 10
  }
}
```

### 1.4 认证和权限

- 登录接口为公开接口，其余接口要求登录。
- 登录成功后从响应的 `data.token` 取得随机 Token。受保护接口通过 `Authorization: <token>` 携带原始 Token，直接填值即可。全局 `LoginInterceptor` 从 Redis 恢复身份，并按 `@RequireRole` 校验角色。
- 管理员接口要求 `ADMIN` 角色；维修人员接口要求 `REPAIRER` 角色；报修人接口要求 `STUDENT` 角色。部分只读接口可按下表标注允许的角色。
- 拦截器从 Redis 登录态读取当前用户 ID 和角色，并放入本次请求的 `loginUser` 属性供 Controller/Service 使用；不接受客户端提交 `userId`、`role` 作为身份依据。列表等涉及资源范围的业务仍须按当前用户角色限制查询数据。
- 初始有效期为 30 分钟，携带有效 Token 访问受保护接口时续期。退出登录会删除当前 Token 对应的 Redis key，缺少或失效的 Token 返回 HTTP `401`。
- 本地开发初始化三种角色的测试账号（报修人、维修人员、管理员），账号数据由数据库初始化脚本创建，不开放公开注册或“首个用户自动成为管理员”接口。仅本地使用的初始密码应使用 BCrypt 等密码哈希存储，禁止把真实密码或可复用生产凭证提交到 Git。
- 浏览器前端将 Token 存入 `sessionStorage`，由 Axios 统一添加请求头。刷新后通过 `GET /auth/me` 恢复身份，退出成功或受保护接口返回 `401` 时清理登录状态。Postman/Apifox 可按角色保存各自的 Token 变量。

### 1.5 枚举值

**工单状态**：`PENDING_ASSIGNMENT`（待派单）、`PENDING_ACCEPTANCE`（待接单）、`ACCEPTED`（已接单）、`PROCESSING`（处理中）、`PENDING_CONFIRMATION`（待确认）、`COMPLETED`（已完成）、`CANCELLED`（已取消）、`CLOSED`（已关闭）。维修人员拒绝动作记为历史 `action=REJECT`，工单直接回到 `PENDING_ASSIGNMENT`，不单独保留 `REJECTED` 当前状态。

**优先级**：`LOW`（低）、`NORMAL`（普通）、`HIGH`（高）、`URGENT`（紧急）。

**角色**：`STUDENT`、`REPAIRER`、`ADMIN`。MVP 每个账号只分配一个业务角色；通过用户角色关联表保存，后续可扩展多角色。

### 1.6 数据库脚本和字段约定

- MySQL 最低版本建议 8.0.16，以确保 `CHECK` 约束会被执行。
- 建表脚本：[schema.sql](../src/main/resources/db/schema.sql)。该脚本创建 `campus_repair` 数据库及核心表；开发者手动运行，不配置为应用每次启动自动重建。
- 数据源配置的数据库名使用 `campus_repair`，例如 `jdbc:mysql://127.0.0.1:3306/campus_repair`；用户名、密码从本地配置或环境变量读取，不写入此文档或提交真实凭证。
- 本地测试数据：[data-dev.sql](../src/main/resources/db/data-dev.sql)。仅用于本机开发，包含报修人、维修人员、管理员账号，类别、楼宇、设备，以及覆盖待派单、处理中、待确认、已完成的工单、历史、附件和评价示例；不能导入生产环境。所有测试账号的本地密码均为 `Dev@123456`。脚本使用 `INSERT IGNORE`，重复执行不会重复添加固定编号的演示数据，也不会删除已有业务记录。
- 表关系：用户、角色、用户角色关系保存账号权限；`ticket` 保存工单当前状态；`ticket_history` 保存状态和派单变化；附件表保存文件路径及元数据；评价与工单一对一。
- 工单创建时保存类别名、楼宇名和设备名快照，避免基础数据改名后历史工单显示内容变化。房间/位置首期作为工单文本字段保存。
- 当前开发配置使用 Redis DB 1。登录态 key 为 `login:token:{token}`，值为用户身份 JSON，包含 `id`、`username`、`name`、`role`。MySQL 保存用户及工单业务数据。
- 工单创建时，服务端根据 `ticket.sla-hours` 计算并保存 `sla_due_at`；默认 48 小时。超时统计只统计 `sla_due_at < 当前时间` 且状态不是 `COMPLETED`、`CANCELLED`、`CLOSED` 的工单。
- `ticket.version` 初始为 0。创建时写入版本 0 的创建历史；每次成功操作使用旧版本做条件更新并令版本加 1，再在同一个事务内写入新版本历史。唯一约束 `(ticket_id, event_version)` 防止同一版本重复写历史。
- 不物理删除用户、楼宇、类别、设备和工单；通过 `enabled` 停用。数据库中 `enabled` 使用 `TINYINT(1)` 存储：`1` 表示启用，`0` 表示停用；接口 JSON 使用布尔值：`true` 对应数据库 `1`，`false` 对应数据库 `0`。因此文档请求/响应示例中的 `true`、`false` 是接口数据类型，不代表数据库列类型。外键限制删除，以保护历史数据。

## 2. 基础数据查询

以下请求示例默认请求前缀为 `http://localhost:8080`，受保护接口使用已登录角色对应的 Token；JSON 请求均设置 `Content-Type: application/json`。

### 2.1 查询启用的故障类别

#### 2.1.1 基本信息

> 请求路径：`/categories`  
> 请求方式：`GET`  
> 接口描述：查询可用于新报修的故障类别。权限：所有已登录角色（`STUDENT`、`REPAIRER`、`ADMIN`）均可调用。

#### 2.1.2 请求参数

无。需要登录。

请求示例：

```http
GET http://localhost:8080/categories
Authorization: <student-token>
```

#### 2.1.3 响应数据

成功时 `data` 为数组，只包含启用状态（`enabled = true`）的故障类别，并按 `sortOrder` 从小到大排序；`sortOrder` 对应数据库字段 `sort_order`。没有启用类别时返回空数组 `[]`。

每项字段如下：

| 字段名 | 类型 | 说明 |
|---|---|---|
| id | number | 故障类别 ID |
| name | string | 类别名称 |
| description | string \| null | 类别说明；没有说明时为 `null` |
| sortOrder | number | 显示顺序，数值越小越靠前 |

成功响应示例：

```json
{
  "code": 1,
  "msg": "success",
  "data": [
    {
      "id": 1,
      "name": "水电",
      "description": "供水、排水、照明及电路故障",
      "sortOrder": 10
    },
    {
      "id": 2,
      "name": "门窗",
      "description": "门锁、门窗及五金故障",
      "sortOrder": 20
    }
  ]
}
```

未登录返回 `401`；已登录但角色不在允许范围内返回 `403`。
### 2.2 管理员维护故障类别

#### 2.2.1 基本信息

> 新增：`POST /admin/categories`；修改：`PUT /admin/categories/{id}`；启用/停用：`PUT /admin/categories/{id}/status`。均需要 `ADMIN` 角色；仅管理员可调用。

#### 2.2.2 请求参数

新增/修改 JSON 字段：`name`（必填，2–50 字）、`description`（选填，最多 200 字）、`sortOrder`（整数，选填；不传时新增默认为 `0`）、`enabled`（boolean，修改时可选；新增不传时默认为 `true`，`true` 启用、`false` 停用）。修改时省略 `description`、`sortOrder` 或 `enabled` 会保留数据库现值；如需清空说明，可传空字符串。状态接口字段：`enabled`（boolean，必填；`true` 启用、`false` 停用）。

#### 2.2.3 响应数据

新增和修改成功时，`data` 返回创建后或更新后的类别对象，字段为 `id`、`name`、`description`、`sortOrder`、`enabled`。启用/停用成功时，`data` 返回更新后的类别状态对象，字段为 `id`、`enabled`。所有成功响应使用统一结构：`code=1`、`msg="success"`。

新增或修改成功响应示例：

```json
{
  "code": 1,
  "msg": "success",
  "data": {
    "id": 6,
    "name": "网络",
    "description": "校园网络和信息点故障",
    "sortOrder": 30,
    "enabled": true
  }
}
```

启用/停用成功响应示例：

```json
{
  "code": 1,
  "msg": "success",
  "data": {
    "id": 6,
    "enabled": false
  }
}
```

业务错误统一返回 `code=0`、`data=null`，用 `msg` 说明原因；业务错误当前通过 HTTP `200` 返回。未登录仍返回 HTTP `401`，角色不符仍返回 HTTP `403`。

新增类别请求示例：

```http
POST http://localhost:8080/admin/categories
Content-Type: application/json
Authorization: <admin-token>

{
  "name": "网络",
  "description": "校园网络和信息点故障",
  "sortOrder": 30
}
```

修改类别请求示例：

```http
PUT http://localhost:8080/admin/categories/6
Content-Type: application/json
Authorization: <admin-token>

{
  "name": "网络故障",
  "description": "校园网络和信息点故障",
  "sortOrder": 30,
  "enabled": true
}
```

启用或停用类别请求示例：

```http
PUT http://localhost:8080/admin/categories/6/status
Content-Type: application/json
Authorization: <admin-token>

{
  "enabled": false
}
```

| `msg` 内容 | 含义 |
|---|---|
| `类别名称不能为空` / `类别名称长度必须为2到50个字符` / `类别说明不能超过200个字符` / `enabled不能为空` | 请求字段缺失或不符合要求 |
| `故障类别不存在` | 修改或启停时指定的类别 ID 不存在 |
| `故障类别名称已存在` | 新增或修改后的类别名称与其他类别重复 |

错误响应使用统一结构，例如重复名称时：

```json
{
  "code": 0,
  "msg": "故障类别名称已存在",
  "data": null
}
```

### 2.5 查询维修人员列表

#### 2.5.1 基本信息

> 请求路径：`/admin/repairers`  
> 请求方式：`GET`  
> 接口描述：管理员派单时查询可用维修人员。权限：仅 `ADMIN`（管理员）可调用。

#### 2.5.2 请求参数

需要 `ADMIN` 角色。可选 Query 参数 `keyword`（姓名或账号，最多 100 字）。

请求示例：

```http
GET http://localhost:8080/admin/repairers?keyword=repairer
Authorization: <admin-token>
```

#### 2.5.3 响应数据

成功响应的 `data` 为数组，仅包含可用于派单的启用维修人员。没有匹配人员时返回空数组。不得返回密码摘要或认证信息。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | number | 维修人员用户 ID，用于提交派单或转派请求 |
| username | string | 账号，用于区分同名人员 |
| name | string | 姓名 |
| phone | string 或 null | 手机号，未填写时为 `null` |
| activeTicketCount | number | 在办工单数量 |
| specialtyCategoryNames | string[] | 擅长维修的故障类别名称。待实现，未登记时返回空数组 |
| responsibleAreaNames | string[] | 负责区域名称。待实现，未登记时返回空数组 |

成功响应示例：

```json
{
  "code": 1,
  "msg": "success",
  "data": [
    { "id": 2002, "username": "repairer001", "name": "维修员甲", "phone": "13800000002", "activeTicketCount": 3, "specialtyCategoryNames": ["水电"], "responsibleAreaNames": ["第一教学楼"] },
    { "id": 2003, "username": "repairer002", "name": "维修员乙", "phone": null, "activeTicketCount": 0, "specialtyCategoryNames": [], "responsibleAreaNames": [] }
  ]
}
```

### 2.6 管理员创建维修人员账号

#### 2.6.1 基本信息

> 请求路径：`/admin/repairers`  
> 请求方式：`POST`  
> 接口描述：管理员创建维修人员账号；角色由服务端固定赋为 `REPAIRER`，不接受客户端传入角色。权限：仅 `ADMIN`（管理员）可调用。

#### 2.6.2 请求参数

需要 `ADMIN` 角色；格式 `application/json`。

| 参数名 | 类型 | 是否必须 | 备注 |
|---|---|---:|---|
| username | string | 是 | 2–64 字，唯一 |
| password | string | 是 | 8–72 字，仅用于创建，不在响应中返回 |
| name | string | 是 | 姓名，1–64 字 |
| phone | string | 否 | 手机号 |

请求示例：

```http
POST http://localhost:8080/admin/repairers
Content-Type: application/json
Authorization: <admin-token>

{
  "username": "repairer003",
  "password": "请替换为本地测试密码",
  "name": "维修员丙",
  "phone": "13800000003"
}
```

#### 2.6.3 响应数据

成功时 `data` 返回 `id`、`username`、`name`、`role`、`enabled`。密码明文和密码哈希均不得返回或记录日志。账号重复返回 `409`。

成功响应示例：

```json
{
  "code": 1,
  "msg": "success",
  "data": { "id": 2004, "username": "repairer003", "name": "维修员丙", "role": "REPAIRER", "enabled": true }
}
```

### 2.7 启用或停用维修人员账号

#### 2.7.1 基本信息

> 请求路径：`/admin/repairers/{id}/status`  
> 请求方式：`PUT`  
> 接口描述：管理员启用或停用维修人员账号；停用账号不可登录或被新派单。权限：仅 `ADMIN`（管理员）可调用。

#### 2.7.2 请求参数

需要 `ADMIN` 角色；格式 `application/json`。

| 参数名 | 类型 | 是否必须 | 备注 |
|---|---|---:|---|
| enabled | boolean | 是 | `true` 启用，`false` 停用 |

请求示例（停用维修人员）：

```http
PUT http://localhost:8080/admin/repairers/2002/status
Content-Type: application/json
Authorization: <admin-token>

{
  "enabled": false
}
```

#### 2.7.3 响应数据

成功返回更新后的 `id`、`enabled`。停用已有工单处理人的账号时，保留其原工单和历史；管理员需另行转派未完成工单。

成功响应示例（停用账号）：

```json
{
  "code": 1,
  "msg": "success",
  "data": { "id": 2002, "enabled": false }
}
```

### 2.8 查询某楼宇的设备

#### 2.8.1 基本信息

成功响应示例：

```json
{
  "code": 1,
```

## 7. 错误响应与业务错误

| HTTP 状态码 | 含义 | 示例 |
|---:|---|---|
| 400 | 参数格式或校验不通过 | 标题为空、分页参数超范围 |
| 401 | 未登录或会话过期 | 未携带有效会话 |
| 403 | 已登录但无该操作权限 | 报修人读取他人工单 |
| 404 | 工单或基础数据不存在 | 查询不存在的工单 ID |
| 409 | 状态冲突、版本冲突或唯一字段冲突 | 重复接单、工单已被其他操作更新 |
| 500 | 未预期的服务端错误 | 服务端内部异常 |

错误响应统一为：

```json
{
  "code": 0,
  "msg": "工单状态已变化，请刷新后重试",
  "data": null
}
```

常见业务错误包括：工单不存在、无权访问、工单当前状态不允许此操作、工单已被其他操作更新、维修人员已停用、故障类别已停用、图片数量或大小超限。客户端响应不包含 SQL、堆栈、服务器路径、密码或 token。

## 8. 分阶段开发计划与接口实施顺序

登录、Redis Token、`LoginInterceptor` 和 `@RequireRole` 已完成。业务接口复用现有认证拦截器和请求属性 `loginUser`。

测试时为每种角色登录一次，在对应的 Apifox 环境中保存 `data.token`。后续请求用 `Authorization` 头引用该环境的 Token，切换角色时切换环境。

### 已完成阶段：登录认证基础设施

- `POST /auth/login`、`GET /auth/me`、`POST /auth/logout` 已实现。
- 全局 `LoginInterceptor` 已对除登录接口外的受保护请求校验登录态；角色要求通过 `@RequireRole` 声明。
- 当前用户从请求属性 `loginUser` 获取；身份依据来自 Redis 登录态，不接受客户端传入的 `userId` 或 `role`。
- 后续 Controller 不重复做登录态检查；Service 不接收 `HttpSession` 做认证。Service/Mapper 仍须实现业务权限和数据归属限制，例如报修人只能访问自己的工单、维修人员只能处理分配给自己的工单。

### 阶段 0：项目与测试数据准备

确认应用、数据库、表结构和开发测试数据可用，准备学生、维修人员、管理员账号。认证已经存在，因此受保护接口测试使用上面的角色 Token 环境。

**阶段验收**：应用成功启动，开发数据库和测试数据可用，三个角色均可登录。

### 阶段 1：统一响应、异常和请求校验

完善统一响应格式、异常处理、字段校验和业务错误映射。

**阶段验收**：非法请求返回约定错误结构，日志不包含密码等敏感信息。

### 阶段 2：基础数据查询和维护

按类别、楼宇、设备和维修人员的顺序，实现对应查询、新增、修改及启用/停用接口；管理员接口使用现有角色拦截规则。

**阶段验收**：基础数据可通过接口读写，停用数据不会被当作有效选项。

### 阶段 3：工单创建、分页列表、详情和历史查询

依次实现工单创建、分页筛选、工单详情和历史查询。查询时使用拦截器提供的 `loginUser` 实施报修人/维修人员的数据范围限制。

**阶段验收**：字段映射、筛选、分页总数、响应内容和角色数据范围正确。

### 阶段 4：管理员派单与维修人员处理

按状态依赖实现派单、接单、处理、拒绝及完成等操作。在同一事务中更新工单并写入历史；并发更新失败时返回冲突且不写历史。

**阶段验收**：正常和异常状态流程正确，重复操作不会覆盖新状态或写出重复历史。

### 阶段 5：报修人确认、重开、取消和管理员关闭

完成报修人确认、重开、取消及管理员关闭接口，并核对状态迁移和角色权限。

**阶段验收**：合法与非法状态变化均返回正确结果，业务数据与历史记录一起提交或回滚。

### 阶段 6：图片上传

实现 `POST /files/ticket-images`，校验数量、大小、扩展名和真实文件类型，使用服务端生成文件名；上传成功后将返回路径用于工单或处理结果。

**阶段验收**：合法图片可上传和访问，超限或伪装类型文件会被拒绝，数据库只保存路径和元数据。

### 阶段 7：统计接口

实现管理员工单统计接口，使用数据库聚合查询，并与工单列表核对统计结果。

**阶段验收**：统计值与对应筛选条件下的工单数据一致。

### 阶段 8：前端联调、回归和交付

前端登录页复用现有登录接口并通过 Token 保持会话，应用启动时可调用 `/auth/me` 恢复当前用户。完成三种角色的端到端流程、异常验证、运行文档和部署配置。

**阶段验收**：三种角色核心流程可重复验证，新环境可按文档启动，前端能正确处理认证、HTTP 错误和业务错误。

## 9. 每个写接口的统一实现检查

实现任何写接口时，按以下顺序逐项完成：

1. 请求字段格式与服务端校验。
2. 复用拦截器提供的 `loginUser`；需要限定角色时在 Controller 上声明 `@RequireRole`，不要在方法里重复校验 Token。
3. 检查工单/基础数据是否存在，以及资源是否属于当前用户可操作范围。
4. 检查当前状态、`expectedVersion` 和重复请求。
5. 在事务内更新业务数据并写状态历史。
6. 明确返回成功、参数错误、未登录、无权限、资源不存在或状态冲突。
7. 用成功、失败、越权、重复请求四类场景验证。
## 10. 当前阶段明确不实现

当前阶段暂不加入消息队列、搜索引擎或定时调度。工单、状态历史、分页和统计以 MySQL 为准。

## 11. Redis 缓存现状与后续开发

### 11.1 已实现的查询缓存

| 接口 | Redis key | 逻辑有效期 / Redis TTL | 写入后失效 |
|---|---|---|---|
| `GET /tickets/{id}` | `cache:ticket:detailed:{id}` | 10～20 分钟 / 20～30 分钟 | 创建及 10 个状态变更操作在 MySQL 事务提交后删除对应详情。 |
| `GET /categories` | `cache:categories:enabled` | 30 分钟 / 40 分钟 | 新增、修改或启停分类写库后删除启用分类列表。 |
| `GET /buildings` | `cache:building:enabled` | 30 分钟 / 40 分钟 | 新增、修改或启停楼宇写库后删除启用楼宇列表。 |
| `GET /buildings/{buildingId}/assets` | `cache:building:asset:{buildingId}` | 10 分钟 / 20 分钟 | 设备新增、修改或启停后清理所属楼宇。跨楼宇迁移清理原楼宇和目标楼宇。楼宇启用状态变化也清理该楼设备列表。 |

四类缓存均按需回填。工单工作台加载时请求分类和楼宇列表，报修表单选择楼宇时请求该楼设备列表。首次查询未命中时回源 MySQL。逻辑过期时可先返回旧值，并由取得锁的后台任务重建。Redis 实际 TTL 比逻辑有效期长 10 分钟，供旧值读取和后台重建使用。工单详情每次回填的逻辑有效期在 15 分钟基础上随机加减 0～5 分钟。

工单详情包含基本信息、报修附件和操作历史。命中缓存后仍根据数据库当前归属校验权限，无权限返回 HTTP `403`。不存在的工单短时缓存空值 1 分钟，并返回 HTTP `404`。列表查询的空数组 `[]` 是有效结果，按列表的正常时长缓存。设备列表查询保留楼宇存在性检查，楼宇已停用时设备查询结果为空。

管理员维护列表、工单分页和统计看板当前直接查 MySQL。统计的超时数依赖当前时间，即使没有写操作也可能变化，刷新时执行实时查询。并发场景下，已读到旧值的后台任务仍可能在删缓存后回填旧数据。

### 11.2 联调与回归

- 工单详情连查两次，确认附件、历史和版本一致。派单后检查下一次查询的状态及版本。无权访问应为 `403`，不存在的工单重复查询均应为 `404`。
- 分类和楼宇列表分别检查首次回填、再次命中、管理员启停后刷新。
- 设备列表已完成联调。回归时先缓存两栋楼的设备列表，再迁移一台设备，确认原楼移除、目标楼新增。停用目标楼后检查设备列表为空。
- 登录已完成前后端联调。回归时验证 30 分钟续期、退出后的旧 Token 失效，以及前端收到 `401` 后清理登录状态。

### 11.3 后续开发建议

| 优先级 | 开发项 | 完成标准 |
|---|---|---|
| P1 | 停用维修员后撤销已有登录态 | `PUT /admin/repairers/{id}/status` 停用成功后，同一账号的多个旧 Token 请求受保护接口均返回 `401`。重新启用后，旧 Token 仍不可用，新登录可以获得新 Token。当前只在登录时检查账号启用状态。 |
| P1 | 补齐楼宇回归测试和参数保护 | 给新增楼宇测试注入 Redis mock，断言删除的 key。将修改楼宇的空请求与缺少名称分开处理，空请求返回参数错误，单独缺少名称保留原名称。 |
| P2 | 验证缓存并发失效 | 复现后台重建与写操作同时发生的场景，验证旧数据是否会在删除后写回。根据复现结果决定是否加回填保护，并验证事务回滚、设备跨楼宇迁移和楼宇停用。 |

| 按需 | 管理列表、楼宇和设备单条详情缓存 | 当前保留 MySQL 查询。实际出现频繁重复查询或明显慢查询时再评估，并为筛选条件、权限和写后失效制定规则。工单分页暂缓加入 Redis。 |

## 12. 操作日志

### 12.1 管理员查询操作日志列表

#### 12.1.1 基本信息

> 请求路径：`/admin/operation-logs`  
> 请求方式：`GET`  
> 接口描述：分页查询操作日志，支持按操作人用户 ID、执行结果和时间范围筛选。仅 `ADMIN` 可调用。

#### 12.1.2 请求参数

需要 `ADMIN` 角色。Query 参数如下：

| 参数 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| userId | number | 否 | 操作人用户 ID，正整数 |
| status | number | 否 | 执行结果，`1` 表示成功，`0` 表示失败 |
| startTime | string | 否 | 开始时间，ISO 8601，包含该时间 |
| endTime | string | 否 | 结束时间，ISO 8601，不包含该时间 |
| page | number | 否 | 页码，从 `1` 开始，默认 `1` |
| pageSize | number | 否 | 每页条数，默认 `10`，最大 `100` |

同时传入 `startTime` 和 `endTime` 时，开始时间必须早于结束时间。参数校验失败返回 `400`。

请求示例：

```http
GET http://localhost:8080/admin/operation-logs?userId=42&status=0&page=1&pageSize=10
Authorization: <admin-token>
```

#### 12.1.3 响应数据

成功时 `data` 使用通用分页结构，记录按 `createdAt` 倒序排列，时间相同时按 `id` 倒序排列。无匹配记录时返回 `total=0`、`rows=[]`。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | number | 日志 ID |
| userId | number 或 null | 操作人用户 ID，未确认身份时为 `null` |
| username | string 或 null | 操作时的用户名，未确认身份时为 `null` |
| methodName | string | 操作方法名，格式为类名.方法名 |
| operation | string | 业务动作 |
| durationMs | number | 方法耗时，单位为毫秒 |
| status | number | 执行结果，`1` 表示成功，`0` 表示失败 |
| targetType | string 或 null | 操作对象类型，未记录时为 `null` |
| targetId | number 或 null | 操作对象 ID，未记录时为 `null` |
| errorCode | string 或 null | 失败错误码，成功或未记录时为 `null` |
| createdAt | string | 日志写入时间，ISO 8601 |

成功响应示例：

```json
{
  "code": 1,
  "msg": "success",
  "data": {
    "total": 1,
    "rows": [
      {
        "id": 101,

        "operation": "分派工单",
        "durationMs": 18,
        "status": 0,
        "targetType": "TICKET",
        "targetId": 1024,
        "errorCode": "TICKET_VERSION_CONFLICT",

      }
    ],

  }
}
```
